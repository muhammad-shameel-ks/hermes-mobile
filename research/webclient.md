## 1. What the web client is, who runs it, how it is served

- Purpose (web/README.md:3): "Browser-based dashboard for managing Hermes Agent configuration, API keys, and monitoring active sessions." Stack: Vite + React 19 + TypeScript, Tailwind CSS v4, shadcn/ui-style components hand-rolled (no CLI dep) (web/README.md:5-9).
- Entry point is the CLI: `hermes dashboard` serves the built bundle; dev is `python -m hermes_cli.main web --no-open` (FastAPI on port 9119) + `npm run dev` (Vite on 5173, `/api` proxied to 127.0.0.1:9119) (web/README.md:11-27, web/vite.config.ts:113-129).
- Build: `web/package.json` build = `node ../scripts/build/web.mjs`; Vite `outDir: "../hermes_cli/web_dist"`, `emptyOutDir: true` (web/vite.config.ts:82-85). Server: `WEB_DIST = Path(__file__).parent / "web_dist"` (hermes_cli/web_server.py:61); mounted by `mount_spa(application)` (hermes_cli/web_server_dashboard.py:103), which serves `/assets/*` immutable, then a catch-all `/{full_path:path}` that returns index.html for SPA routes but a real JSON 404 under `api/` (hermes_cli/web_server_dashboard.py:212-232).
- `hermes serve` (headless backend the DESKTOP spawns) disables the SPA entirely via `HERMES_SERVE_HEADLESS=1`; it serves only a token-only root page for the Electron handshake (hermes_cli/web_server_dashboard.py:104-140). Desktop therefore has no runtime dependency on this frontend (web/AGENTS.md:29-33).
- Reverse-proxy support: `X-Forwarded-Prefix` is read per request; index.html asset URLs are rewritten and `window.__HERMES_BASE_PATH__` is injected so the SPA can prefix its own `/api/...` calls without a rebuild (hermes_cli/web_server_dashboard.py:141-181, web/src/lib/api.ts:16-32).
- Client-side routes (App.tsx:141-226): `/chat`, `/sessions`, `/files`, `/analytics`, `/models`, `/logs`, `/cron`, `/skills`, `/plugins`, `/mcp`, `/channels`, `/webhooks`, `/pairing`, `/profiles`, `/config`, `/env`, `/system`, `/docs`, plus plugin routes and a `*` fallback; all pages are `React.lazy` (App.tsx:82-100).
- Design rules worth copying for parity: 12px text floor, never opacity < 0.7 on text, semantic tokens `text-text-primary/secondary/tertiary/disabled/on-accent`, brand uppercase only via `text-display`, font tiers `font-mondwest`/`font-expanded`/`font-mono-ui` (web/README.md:44-120).

### 1a. Auth - the answer

Two mutually exclusive deployment modes; the SPA learns which from injected globals.

**Loopback / `--insecure` (token mode).**
- Server mints `_SESSION_TOKEN = os.environ.get("HERMES_DASHBOARD_SESSION_TOKEN") or secrets.token_urlsafe(32)`; it dies with the process (hermes_cli/web_server.py:379-387). Header name `X-Hermes-Session-Token` (web_server.py:387); REST accepts that header or `Authorization: Bearer <token>` (web_server.py:464-468); a query `?token=` is allowed only on routes that opted in (web_server.py:471-480).
- The token is injected into index.html as `window.__HERMES_SESSION_TOKEN__` together with `__HERMES_DASHBOARD_EMBEDDED_CHAT__`, `__HERMES_BASE_PATH__`, `__HERMES_AUTH_REQUIRED__`, `__HERMES_INITIAL_PROFILE__`, `__HERMES_DASHBOARD_PROFILE__` (hermes_cli/web_server_dashboard.py:160-181), served `Cache-Control: no-store`. The Vite dev server scrapes the same globals from the running dashboard and re-injects them (web/vite.config.ts:29-79).
- Client: `fetchJSON` attaches the header if present and always sets `credentials: init?.credentials ?? "include"` (web/src/lib/api.ts:161-187); `authedFetch` mirrors it for blobs/FormData (api.ts:316-334).
- Token rotation: if the html is stale the server token has changed, so the first 401 (in non-gated mode) triggers ONE full-page reload via sessionStorage guard (api.ts:228-247, web/src/lib/dashboard-auth-reload.ts:34-57).
- WS auth uses a query param because browsers cannot set headers on an upgrade: `?token=<_SESSION_TOKEN>`, constant-time compared (hermes_cli/web_server_chat.py:373-375).

**Gated (public bind without `--insecure`, OAuth).**
- The legacy token is deliberately NOT injected: `token_js = "" if gated else ...` (web_server_dashboard.py:164-165); `__HERMES_AUTH_REQUIRED__=true` (web_server_dashboard.py:172-173). Identity comes from cookies or a bearer.
- Cookies: `hermes_session_at` (Max-Age = provider token TTL), `hermes_session_rt` (rotating refresh, Max-Age 30d), `hermes_session_provider` (routing hint), `hermes_session_pkce` (10 min), `hermes_sso_attempt` (60s loop guard); all HttpOnly, SameSite=Lax (PKCE cookie SameSite=None over HTTPS), Path=prefix or `/`, name variants `__Host-`/`__Secure-`/bare chosen by scheme+prefix (hermes_cli/dashboard_auth/cookies.py:1-14, 26-31, 43-56, 97-113).
- Gate middleware: public prefixes are `/auth/login`, `/auth/callback`, `/auth/native/authorize`, `/auth/native/token`, `/auth/native/refresh`, `/auth/password-login`, `/auth/logout`, `/login`, `/api/auth/providers`, `/api/mcp/oauth/callback/`, `/assets/`, `/dashboard-plugins/`, `/favicon.ico`, `/ds-assets/`, `/fonts/`, `/fonts-terminal/` (hermes_cli/dashboard_auth/middleware.py:39-43). Everything else needs cookie or bearer; `/api/*` gets `401 {error: "unauthenticated"|"session_expired", detail, reason, login_url}`, HTML gets 302 to `/login` (middleware.py:79-92). Expired AT with live RT is silently rotated (single-flight, reuse-detection safe) (middleware.py:193-232).
- Client: `fetchJSON` parses that 401 envelope and does `window.location.assign(body.login_url)` after stashing `sessionStorage["hermes.lastLocation"]`; it never resolves (api.ts:190-226).
- WS in gated mode: `POST /api/auth/ws-ticket` mints a single-use 30s ticket (hermes_cli/dashboard_auth/routes.py:556-559, ws_tickets.py:4-8); `buildWsAuthParam()` returns `["ticket", t]` when `window.__HERMES_AUTH_REQUIRED__` else `["token", token]` (api.ts:290-297). Server accepts `?ticket=`, a ticket-bearing subprotocol, `?internal=` (server-spawned clients only) or `?token=<user session access token>` verified through the provider stack; the legacy `_SESSION_TOKEN` is explicitly rejected in gated mode (web_server_chat.py:250-380).
- Close codes: 4401/4403 mean the credential is dead and retrying is pointless; 4410 = PTY child exited; 4409 = another tab took the attach token; 1000 = intentional (web/src/lib/events-reconnect.ts:24-46, web/src/pages/ChatPage.tsx:1433-1437).

**Cookie-free bearer path for native apps (the one RN must use).**
- `GET /auth/native/authorize` starts an RFC 8252 native-app login; the gateway brokers an OAuth client to the Portal and mints a one-time loopback code bound to the app's PKCE challenge (`cv_d`/`cc_d`, `broker_state`) (hermes_cli/dashboard_auth/routes.py:7-16, 289-314; native_flow.py:1-33).
- `POST /auth/native/token` exchanges loopback code + PKCE verifier for bearer tokens; `POST /auth/native/refresh` rotates the refresh token (routes.py:574-597). The same access token is accepted on REST as `Authorization: Bearer` and on the WS upgrade as `?token=` (middleware.py:120-124, web_server_chat.py:326-372). No cookies involved anywhere on this path.
- The live desktop registry already uses this mode: `~/.config/Hermes/connections.json` has `{id:"local",kind:"local"}` and `{id:"omarchy-zeus",kind:"remote",url:"https://hermes.shameel.dev",authMode:"oauth"}`; the desktop mints a fresh WS URL per connect rather than caching a ticket (apps/shared/src/websocket-url.ts:33-95, apps/desktop/src/store/gateway.ts:835-839).
- What a mobile client must differ on: RN has no cookie jar, so gated cookie auth is unusable; use `/auth/native/*` + `expo-secure-store` for AT/RT, refresh via `/auth/native/refresh`, send `Authorization: Bearer` on REST and `?token=<AT>` on WS [INFERENCE - standard RN constraint, not stated in-repo].

## 3. UI: reuse vs separate, quantified

- **Zero cross-app UI sharing.** A repo-wide search for imports of `apps/desktop`/`@hermes/desktop` from other apps returns only test-harness/script references (`evals/desktop-pane-fixture/vitest.config.mts:5`, `scripts/build/desktop.mjs:6-9`, `tests-js/*`) - no `web/` file imports any desktop component, and web/package.json has no desktop dependency. The only shared artifact is `@hermes/shared` (protocol/types) plus the external design system `@nous-research/ui@0.18.2`.
- Web UI is its own simpler stack: Tailwind v4 + hand-rolled shadcn-style primitives + `@nous-research/ui` DS components. 44 files under `web/src` import the DS, e.g. `web/src/App.tsx:59-67` (Button, SelectionSwitcher, Spinner, Typography, ConfirmDialog, useBelowBreakpoint), first entry is `./ui/*` subpaths as in `@nous-research/ui/ui/components/button`.
- DS portability: `@nous-research/ui` is DOM/Radix/Tailwind bound - deps `radix-ui`, `@nanostores/react`, `sanitize-html`, `clsx`, `tailwind-merge`, `tw-animate-css`; peerDeps react/react-dom/three/gsap/leva/motion; exports `./ui/*`, `./hooks/*`, `./styles/globals.css` (node_modules/@nous-research/ui/package.json). **Not usable from React Native.**
- The single biggest UI divergence from the desktop: the web Chat tab is an embedded `hermes --tui` inside xterm.js (WebGL renderer, fit + unicode11 addons, 5000-line scrollback, screenReaderMode) (web/AGENTS.md:6-14, web/src/pages/ChatPage.tsx:538-543), and web/AGENTS.md:20-27 explicitly forbids re-implementing the transcript/composer in React for the dashboard. The DESKTOP is the opposite: its own assistant-ui transcript, composer, slash pipeline over JSON-RPC (apps/desktop/src/AGENTS.md:1-13). So "mirror the desktop UI/UX" in RN means targeting the desktop's React surfaces + JSON-RPC contract; the web dashboard is a management console, not a desktop-UI reference.
- Quantified overlap for an RN app: reusable code ~ one package (`@hermes/shared`, ~19 subpath exports, all plain TS) + ~15 pure helper modules from `web/src/lib`; **not** reusable: all of `web/src/components` (44 DS-importing files + more), all `web/src/pages` (23 pages), `web/src/themes/*` (CSS-variable projection), `web/src/i18n/context.tsx` (React), xterm/PTY terminal stack, localStorage/sessionStorage persistence, DOM modal/portal helpers.

## 6. Concrete guidance for the RN client (derived, not a new decision)

1. Chat surface: talk JSON-RPC to `/api/ws` (same methods the desktop uses: `session.create/resume/list`, `prompt.submit`, `commands.catalog`, `complete.*`, `slash.exec`, `command.dispatch`, `approval.respond`, `clarify.lock`, `client.capabilities`), and render the transcript from `message.*`/`tool.*`/`session.*` events yourself. Do NOT try to mirror the web's PTY+xterm path: it exists to embed `hermes --tui`, and the desktop deliberately does not use it (apps/desktop/src/AGENTS.md:1-13). An RN PTY mirror would additionally need `.js`/`.ts` free byte handling and the resize escape protocol described above.
2. Reuse `@hermes/shared` verbatim (subclass `JsonRpcGatewayClient` exactly like `GatewayClient`/`EventsFeedClient` do): pass `socketFactory` if needed, call `client.capabilities` after `gateway.ready`, keep the default 120s request / 300s approval timeouts, and keep the seq-based replay (`session.events.since`) since it is what makes reconnect lossless.
3. Base URL + auth: gated servers require `/auth/native/authorize` -> `/auth/native/token` (PKCE) -> `/auth/native/refresh`, then `Authorization: Bearer` and `?token=<AT>` on WS; loopback/LAN servers can keep the simpler `?token=<_SESSION_TOKEN>` scheme only if you can read the token out of the served index.html the way the Vite dev plugin does (web/vite.config.ts:29-79, `window.__HERMES_SESSION_TOKEN__`). Always pass explicit `protocol`/`host` to `buildHermesWebSocketUrl`.
4. Port `PROFILE_SCOPED_PREFIXES` + `?profile=` semantics into the RN REST client or the management routes will 400 on any multi-profile host (web/src/lib/api.ts:94-145 and the comment block at 147-160 explaining why an unnamed profile is refused).
5. Theme parity: use `@hermes/shared/theme-presets` (`THEME_PRESET_PALETTES`) plus `@hermes/shared/color` for the same colours the desktop/web project from, instead of copying hexes.
